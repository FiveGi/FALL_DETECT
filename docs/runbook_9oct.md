# คู่มือวันทดสอบระบบ 9 ต.ค. 2026 (ร่าง v2 — ต้องให้ Codex + Gemini ตรวจ)

ระบบ: ตรวจจับการล้มของผู้สูงอายุจากกล้องวงจรปิด รันบน server (CPU 4 core ไม่มีการ์ดจอ) รับภาพจากกล้อง IP ผ่าน RTSP หรือจากคลิปทดสอบ แจ้งเตือนบนหน้าเว็บและ LINE

ทีมพัฒนาเข้า server เองไม่ได้ → **คนที่เข้า server ได้เป็นคนทำข้อ 0** แล้วส่งผลลัพธ์ที่บอกให้ "ส่งให้ทีม" กลับมา (ผ่านเจ้าของโครงการ) ทีมจะตอบคำสั่งที่ต้องใช้ต่อ

ช่องที่มี [เติม] = รอข้อมูลจากข้อ 0.1

## 0. อัปเดตระบบบน server เป็นเวอร์ชันทดสอบ (คนที่เข้า server ได้ ทำก่อนวันทดสอบ ~30 นาที)

เวอร์ชันที่จะใช้: ป้าย (tag) **`systest-2026-10-09`** รหัส commit **[เติม: SHA ตอนหยุดแก้โค้ด 8 ต.ค. 12:00]**

**กฎ: ถ้าขั้นไหนขึ้นข้อความ error หรือผลไม่ตรงที่เขียนไว้ → หยุดทันที ส่งข้อความนั้นให้ทีม ห้ามลองแก้เอง ห้ามสั่ง `git stash` / `git reset`**

### 0.1 สำรวจ (ไม่เปลี่ยนอะไรเลย) — ส่งผลทั้งหมดให้ทีม
```
cd [เติม: โฟลเดอร์โปรเจกต์บน server]
git remote -v
git lfs version
nproc; lscpu | grep -iE 'on-line|off-line'
git rev-parse --abbrev-ref HEAD
git log -1 --format='%H %ci %s'
git status --short
docker compose ps
docker ps --format '{{.Names}}  {{.Image}}  {{.Ports}}'
ps aux | grep -E 'vite|npm run|node ' | grep -v grep
docker compose exec -T db psql -U postgres -d postgres -tA -c "select count(*) from cameras; select count(*) from notification_history;"
```
- ถ้า `docker` ขึ้น `permission denied` → ใส่ `sudo ` หน้าคำสั่ง `docker ...` **และ** `bash tools/...` ทุกบรรทัดในคู่มือนี้
- ถ้า `git status --short` **มีบรรทัดใดๆ** แปลว่ามีไฟล์ที่ถูกแก้บน server → **หยุด ส่งให้ทีม** (ทีมจะบอกวิธีเก็บค่าเดิมไว้)
- บรรทัด `docker ps` / `ps aux` บอกว่าหน้าเว็บ (frontend) รันแบบไหน → ทีมจะส่งคำสั่งอัปเดตหน้าเว็บที่ตรงกับแบบนั้น (ข้อ 0.4)

### 0.2 สำรองข้อมูล
```
STAMP=$(date +%Y%m%d-%H%M); mkdir -p ~/backup-$STAMP
cp .env ~/backup-$STAMP/.env
git rev-parse HEAD > ~/backup-$STAMP/commit.txt
docker compose exec -T db pg_dump -U postgres postgres > ~/backup-$STAMP/db.sql
ls -la ~/backup-$STAMP
grep -c "CREATE TABLE" ~/backup-$STAMP/db.sql
echo "backup = ~/backup-$STAMP"
```
- เก็บไว้ในโฟลเดอร์บ้านของผู้ใช้ (`~`) ซึ่งเขียนได้เสมอ และไม่ปนกับโฟลเดอร์โปรเจกต์
- `db.sql` ต้องไม่ใช่ 0 ไบต์ และตัวเลข CREATE TABLE ต้องมากกว่า 0 → **จดชื่อโฟลเดอร์ backup ไว้** (ใช้ตอนย้อนกลับ)

### 0.3 ดึงเวอร์ชันใหม่
```
git fetch origin --tags
git rev-parse 'systest-2026-10-09^{commit}'
```
- ตัวเลขที่ได้ต้อง**ตรงกับรหัส commit ด้านบน** ทุกตัวอักษร ถ้าไม่ตรง → หยุด
```
git checkout systest-2026-10-09
```
- ถ้าขึ้น `error: Your local changes ... would be overwritten` → หยุด ส่งให้ทีม (ห้ามใช้ `-f`)
- ข้อความ `You are in 'detached HEAD' state` = ปกติ ไม่ต้องทำอะไร
```
git lfs pull
ls -la models/fall_classifier_v3.onnx models/fall_classifier_t2full_s45.onnx Test/14.mp4
```
- ไฟล์โมเดลและคลิปเก็บด้วย Git LFS: ทุกไฟล์ในบรรทัด `ls` ต้องใหญ่กว่า **100 KB** (ถ้าเห็นไฟล์ราว 130 ไบต์ = ได้แค่ "ไฟล์ชี้" ไม่ใช่ไฟล์จริง → หยุด ส่งให้ทีม)
- ถ้า `git lfs version` ในข้อ 0.1 ขึ้น `not a git command` → หยุด ส่งให้ทีม (ต้องติดตั้ง git-lfs ก่อน)

- **หน้าเว็บ (frontend) ต้องอัปเดตพร้อมกันเสมอ** ไม่อย่างนั้นหน้าดูกล้องสดจะใช้ไม่ได้ — ทำตามคำสั่งที่ทีมส่งให้จากผลข้อ 0.1:
  - ถ้ารันด้วย `npm run dev` จากโฟลเดอร์นี้ → ไม่ต้องทำอะไร (โหลดไฟล์ใหม่เอง) แค่กด refresh หน้าเว็บ

  - ถ้าเป็นไฟล์ที่ build แล้ว (nginx) → `cd frontend && npm install && npm run build` (ทีมยืนยันก่อน)
- เปิดหน้าเว็บ → เข้าสู่ระบบ → เปิดทุกเมนู ต้องไม่มีหน้าว่าง; หน้า "มอนิเตอร์" ต้องเห็นประวัติแจ้งเตือนเดิม

## 1. ก่อนเริ่ม (ทำครั้งเดียว ก่อนเริ่มทดสอบ ~15 นาที)

1. เข้า server แล้วไปที่โฟลเดอร์โปรเจกต์: `cd [เติม: path บน server]`
2. ดูว่าระบบรันอยู่: `docker compose ps` → ต้องเห็น backend, celery_worker, celery_maintenance (ตัวส่งเตือนซ้ำ), celery_beat, db, redis สถานะ `Up`
3. เปิดหน้าเว็บ: `[เติม: https://...]` → เข้าสู่ระบบได้
4. เช็กว่าใช้โมเดลตัวไหน: `docker compose logs celery_worker | grep "model identity" | tail -1`
   - **ค่าเริ่มต้นของเวอร์ชันนี้ = โมเดลตัวเดิม** (เจ้าของตัดสิน 8 ต.ค.): `classifier: fall_classifier_v3.onnx`, `pose: yolo26s-pose.pt`, `threshold: 0.65`
   - ถ้าสลับไปใช้ตัว A (ข้อ 5): `classifier: fall_classifier_t2full_s45.onnx`, `pose: pose_nightaug_s44.pt`, `threshold: 0.7`
5. เช็กเวลา server เป็นเวลาไทย: `docker compose exec backend date` → ต้องตรงกับนาฬิกาจริง

## 2. เพิ่มกล้อง และเช็กกล้องตัวแรก 5 นาที

1. หน้าเว็บ → จัดการกล้อง → เพิ่มกล้องใหม่ → ชนิดการตรวจ **"ตรวจจับการล้ม — โมเดลปัจจุบัน YOLO-pose (แนะนำ)"** → แหล่งวิดีโอ "พิมพ์ URL" → ใส่ RTSP
   - รูปแบบ: `rtsp://ผู้ใช้:รหัส@IP:554/...` (ดูคู่มือกล้อง)
   - **ถ้ากล้องมี substream (ความละเอียดต่ำ) ให้ใช้ substream** — ประหยัด CPU มาก
2. กด "เริ่มตรวจ" แล้วรอ 1–2 นาที
3. เช็กว่ากล้องเปิดได้และเร็วพอ: `docker compose logs --since 3m celery_worker | grep "Detection rate"`
   - ดูตัวเลข `Detection rate: X/8 fps` → **X ควรตั้งแต่ 6 ขึ้นไป**
   - ถ้าเห็น `lost the video stream` หรือ `cannot open the video stream` ซ้ำๆ → ดูข้อ 7 (แก้ปัญหา)
4. เดินผ่านหน้ากล้อง ดูว่าหน้าเว็บ (มอนิเตอร์) เห็นภาพ

## 3. ใช้กล้องได้กี่ตัว (วัดบนเครื่องพัฒนาที่จำกัดไว้ 4 core ด้วยกล้องจำลอง, 6 ต.ค. — **ยังไม่ได้วัดบน server จริง** ซึ่ง CPU ช้ากว่า ให้ดูตัวเลข Detection rate จริงในวันนั้น)

| จำนวนกล้อง | ความละเอียด | ภาพต่อวินาทีต่อกล้อง | คำแนะนำ |
|---|---|---|---|
| 1–2 | 1080p | ~7.2 | ใช้ได้ |
| 3 | 1080p | ~5.7 | ไม่แนะนำ — ใช้ substream |
| 4 | 1080p | ~4.0 | **ห้ามใช้** — จับล้มได้น้อยลงมาก |
| 4 | 720p | ~5.6 | ต่ำกว่าเกณฑ์ 6 — ใช้ 360p แทน |
| 4 | 360p (substream) | ~6.8 | ดีที่สุดสำหรับ 3–4 กล้อง |

วัดซ้ำด้วยคลิปทดสอบจริง (7 ต.ค., เครื่องพัฒนา จำกัด 4 core; คลิป 14 = 1080p, 15/16 = 720p, 1 = 576×1024):

| จำนวนกล้อง | ภาพต่อวินาทีต่อกล้อง |
|---|---|
| 1 | ~6.8 (รวมช่วงเริ่ม) |
| 2 | 7.2–7.6 |
| 3 | 6.5–7.0 |
| 4 | 5.3–5.9 (ต่ำกว่าเกณฑ์ 6) |

**ตัวเลขทั้งหมดนี้วัดบนเครื่องพัฒนา ยังไม่ได้ยืนยันบน server** — server เป็นเครื่องเสมือนที่ core ช้ากว่า ให้ถือตัวเลขจริงจาก `Detection rate` ในวันนั้น

กฎง่าย:
- **1–2 กล้อง ใช้ภาพปกติได้; 3–4 กล้อง ใช้ substream (ความละเอียดต่ำ)**
- ถ้าตั้งค่ากล้องได้ ให้ลดเฟรมเรตของกล้องเหลือ 10–15 ภาพต่อวินาที (ระบบใช้แค่ 8) — ประหยัด CPU ที่ใช้ถอดรหัสภาพ
- **ถ้า Detection rate ต่ำกว่า 6 → ลดความละเอียดหรือจำนวนกล้อง**

## 4. LINE

- สวิตช์ที่ใช้จริงคือ**สวิตช์ของผู้ใช้ในหน้าเว็บ "ตั้งค่าการแจ้งเตือน"** (`LINE_ENABLED` ใน `.env` ใช้แค่ตอนสร้างการตั้งค่าครั้งแรก)
- ปุ่ม "รับทราบ" ใน LINE **(ไม่บังคับ — ถ้าทำไม่ได้ ข้ามไป ใช้ปุ่มรับทราบในหน้าเว็บแทนได้เหมือนกัน)** ต้องตั้งครบ 3 อย่าง (คนที่ดูแลบัญชี LINE Official Account ทำ): (1) ใน LINE Developers Console → เลือก channel → แท็บ Messaging API → Webhook URL = `[เติม: https://<server>]/api/line/webhook` → กด Verify → เปิด Use webhook (2) `LINE_CHANNEL_SECRET` ใน `.env` (แท็บ Basic settings → Channel secret) (3) `PUBLIC_BASE_URL=[เติม: https://<server>]` ใน `.env` → แล้ว `docker compose up -d`
  - ถ้าใน `.env` **ไม่มี** `LINE_CHANNEL_SECRET` หรือ `PUBLIC_BASE_URL` → ระบบจะไม่แสดงปุ่ม ข้อความ LINE จะลงท้ายว่า "กดรับทราบได้ที่หน้าเว็บ เมนู 'มอนิเตอร์'" (หน้า "ตั้งค่าการแจ้งเตือน" บอกว่าขาดอะไร)
  - ถ้าใส่ค่าครบแล้ว ปุ่มจะขึ้น **แต่ระบบไม่รู้ว่าปุ่มกดได้จริงไหม** (เช่น ลืมเปิด Use webhook, URL ผิด) → **ต้องลองกดปุ่มจริงจากมือถือ 1 ครั้ง** แล้วดูในหน้า "มอนิเตอร์" ว่าขึ้น "รับทราบแล้ว" — ถ้าไม่ขึ้น ให้กดรับทราบในหน้าเว็บตลอดการทดสอบ
- **แจ้งเตือน "⚠️ พบว่ามีคนอยู่ตามลำพัง" เปิดอยู่** (เจ้าของตัดสิน 7 ต.ค.): ส่งเข้า LINE ทุกช่วงพัก (NOTIFICATION_COOLDOWN) ต่อกล้อง เมื่อเห็นคนเดียวในภาพ — เป็นเรื่องปกติ ไม่ใช่ระบบรวน
- รูปใน LINE ต้องมี `PUBLIC_BASE_URL` เป็นลิงก์ HTTPS ที่คนนอกเปิดได้
- **ก่อนเปิด LINE ทุกครั้ง**: เช็กว่าไม่มีการเตือนเก่าค้าง (ไม่อย่างนั้นระบบจะส่งซ้ำเข้ามือถือ): `bash tools/line_backlog.sh check` → ถ้าบรรทัด "could still be re-sent" ไม่ใช่ 0 ให้รัน `bash tools/line_backlog.sh clear` (การเตือนเก่ายังอยู่ในประวัติ แค่หยุดส่งซ้ำ)
  - **ถ้าขึ้น `LINE BACKLOG CHECK FAILED` → ห้ามเปิด LINE** ส่งข้อความนั้นให้ทีม
- กดปุ่ม "ส่งข้อความทดสอบ" 1 ครั้ง → ต้องได้ข้อความใน LINE
- ข้อความที่จะได้รับ:
  1. **เตือนครั้งแรก**: "❓ อาจมีการล้ม — รบกวนตรวจสอบกล้องด้วยครับ" + รูป + ปุ่ม "รับทราบ"
  2. **ยังนอนอยู่**: "🚨 ตรวจพบคนล้ม และยังไม่ลุกขึ้นเลยเป็นเวลา N วินาที — กรุณาไปดูด่วน!" — ระบบเช็กหลังเตือนครั้งแรกอย่างน้อย 10 วินาที (STILL_DOWN_SECONDS=10) และส่งเฉพาะถ้ากล้องยังเห็นคนนอนอยู่; ส่งครั้งเดียว และไม่ส่งถ้ากดรับทราบแล้ว
  3. **เตือนซ้ำ**: "🔁 แจ้งซ้ำครั้งที่ N — ยังไม่มีใครกดรับทราบ" เมื่อผ่านไป 3 นาทีแล้วยังไม่มีคนกดรับทราบ (ESCALATION_DELAY_MINUTES=3; ระบบตรวจทุก 60 วินาที; ครั้งที่ 2 ตามมาในรอบถัดไป ~1 นาทีต่อมา) สูงสุด 2 ครั้ง (MAX_ESCALATIONS=2; นับเฉพาะที่ส่งถึงจริง) และเฉพาะการเตือนที่อายุไม่เกิน 30 นาที — ข้อความ "🔁 แจ้งซ้ำครั้งที่ N — ยังไม่มีใครกดรับทราบ" ตามด้วย "🚨 ยังไม่มีใครตรวจสอบการแจ้งเตือนล้ม — กรุณาไปดูด่วน!"
- กด "รับทราบ" ใน LINE → หยุดเตือนซ้ำ และหยุดข้อความ "ยังนอนอยู่"
- ล้ม 1 ครั้ง = ข้อความครั้งแรก 1 ครั้ง ภายในช่วงพัก (ถ้าคนยังทำท่าคล้ายล้มหลังหมดช่วงพัก ระบบเตือนใหม่ได้) — ช่วงพักกันซ้ำต่อกล้อง = NOTIFICATION_COOLDOWN ใน .env (ค่าเริ่มต้นของระบบ 60 วินาที — เครื่องทดสอบตั้ง 600 วินาที = 10 นาที; [เติม: ค่าบน server]; แม้ระบบรีสตาร์ทก็ยังจำ)

## 5. สลับโมเดล / ถอยกลับ

- เวอร์ชันนี้ใช้**โมเดลตัวเดิมเป็นค่าเริ่มต้น**อยู่แล้ว (ตั้งไว้ใน docker-compose.yml) — **ไม่ต้องแก้ `.env`**
- ทำไมไม่ใช้ตัว A เป็นค่าเริ่มต้น: ตัว A จับล้มกลางคืนได้ดีกว่า แต่**เห็นเฟอร์นิเจอร์เป็นคน**ในห้องว่าง → แจ้ง "อยู่ตามลำพัง" ผิด (ทดสอบ 4 ชม.: 24 ครั้ง)
- **สลับไปใช้ตัว A** (เฉพาะเมื่อตกลงกันแล้ว): พิมพ์ `nano .env` → เลื่อนลงล่างสุด → พิมพ์เพิ่ม 3 บรรทัดนี้ → กด Ctrl+O, Enter, Ctrl+X
  ```
  V3_POSE_MODEL=pose_nightaug_s44.pt
  V3_CLASSIFIER=fall_classifier_t2full_s45.onnx
  V3_THRESHOLD=0.70
  ```
- **กลับมาใช้ตัวเดิม**: `nano .env` → ลบ 3 บรรทัดนั้น → Ctrl+O, Enter, Ctrl+X
- ทุกครั้งที่แก้ `.env`: `docker compose up -d --force-recreate` แล้วเช็ก "model identity" (ข้อ 1.4) — บรรทัดนั้นขึ้นหลังเริ่มตรวจกล้องตัวแรก
- ถอยกลับทั้งระบบเป็นเวอร์ชันก่อนอัปเดต: ข้อ 0.5

## 8. จุดอ่อนที่รู้แล้ว (บอกผู้ทดสอบล่วงหน้า)
- กลางคืน: บางครั้งมองไม่เห็นคนที่นอนอยู่บนพื้น
- หลายคนในภาพ: บางครั้งเตือนผิดคน
- คนที่ตั้งใจลงพื้นเองจะถูกเตือน (ยอมรับได้ตามที่ตัดสินไว้)
- ภาพต่อวินาทีต่ำ (กล้องเยอะ/ความละเอียดสูง) → จับล้มได้น้อยลง

## 9. ทดสอบด้วยคลิป (ใช้ซ้อมก่อนวันจริง หรือใช้บน server ถ้ายังไม่มีกล้อง)

หน้าเว็บ → จัดการกล้อง → เพิ่มกล้องใหม่ → แหล่งวิดีโอ **"ไฟล์วิดีโอทดสอบ"** → เลือกคลิป → เริ่มตรวจ. คลิปจะเล่นวนซ้ำ ทำทีละ 1 กล้อง แล้ว**รับทราบ → หยุดกล้อง** ก่อนเปลี่ยนคลิป
- ก่อนเพิ่มคลิปถัดไป ดูหน้า "จัดการกล้อง" ว่า**มีกล้องที่กำลังตรวจอยู่ไม่เกิน 1 ตัว** — ถ้าลืมหยุด กล้องหลายตัวจะแย่ง CPU กัน (ข้อ 3) และจับล้มได้น้อยลง
